## 项目介绍

本项目是一个企业级的智能文档问答系统，旨在解决传统文档检索效率低、大模型幻觉等痛点。通过 RAG（检索增强生成）技术，系统能够基于用户上传的私有文档（PDF、Word、Markdown 等）进行精准问答，让 AI 回答有据可查。

**核心价值：**

- 📚 **知识沉淀**：将分散的文档转化为可检索的知识库
- 🔍 **精准检索**：混合检索 + 重排序，找到最相关的文档片段
- 🤖 **智能回答**：基于检索内容生成答案，杜绝幻觉
- 👥 **多租户隔离**：JWT 鉴权，用户数据完全隔离

**适用场景：**

- 企业内部知识库问答（产品手册、技术文档、规章制度）
- 智能客服辅助（基于历史工单和 FAQ）
- 个人知识管理（论文、笔记、资料整理）

## 技术选型说明

### 为什么选这些技术？

| 技术          | 选型                    | 理由                                |
| ------------- | ----------------------- | ----------------------------------- |
| **后端框架**  | FastAPI                 | 异步高性能、自动 API 文档、类型提示 |
| **数据库**    | PostgreSQL + pgvector   | 成熟稳定、事务支持、向量扩展成熟    |
| **前端**      | Streamlit               | 快速原型、Python 生态、适合演示     |
| **Embedding** | BAAI/bge-m3             | 中文效果 SOTA、开源可商用、1024 维  |
| **Rerank**    | BGE-Reranker-v2-m3      | 轻量高效、与 bge-m3 同生态          |
| **LLM**       | DeepSeek-chat / Qwen2.5 | 中文能力强、API 成本低              |
| **缓存**      | Redis                   | 高性能、支持 TTL、分布式            |
| **部署**      | Docker Compose          | 环境一致、一键启动、易扩展          |

### 关键设计决策

1. **混合检索而非纯向量**：向量检索擅长语义匹配，BM25 擅长精确匹配，两者互补
2. **Rerank 二次排序**：粗排召回更多候选，精排确保最相关的进入 LLM
3. **异步处理**：文档解析用后台任务，避免上传接口阻塞
4. **连接池 + 限流**：防止高并发打垮数据库和外部 API

## 已解决的问题

### 🔴 严重问题

#### 1. Embedding 模型配置错误导致全量向量失效

**现象**：所有文档检索相似度极低（0.02-0.05）
**根因**：误将 LLM 模型 `deepseek-chat` 配置为 Embedding 模型
**解决**：修正为 `BAAI/bge-m3`，清空数据库重新索引
**教训**：配置校验很重要，启动时检查模型名称是否匹配

#### 2. 混合检索 SQL NULL Bug

**现象**：查询返回 0 个 chunks，LLM 回答"文档空白"
**根因**：`FULL OUTER JOIN` + `MAX(text_score)` 在 text_scores 为空时返回 NULL
**解决**：重写为 UNION-based 实现，Python 端做分数融合
**教训**：SQL 聚合函数要注意 NULL 处理，复杂查询先在数据库客户端验证

#### 3. 后台任务共享 DB Session 导致异步冲突

**现象**：文档解析完成后偶发数据库连接错误
**根因**：后台任务复用请求 session，异步关闭后访问报错
**解决**：后台任务使用独立的 `SessionLocal`
**教训**：异步场景下 session 生命周期要独立管理

### 🟡 性能问题

#### 4. LLM 过度保守拒绝回答

**现象**：检索到文档但 LLM 说"根据已有信息无法回答"
**根因**：temperature=0.3 + frequency/presence penalty 让模型太谨慎
**解决**：temperature 调至 0.7，移除 penalty，优化 prompt
**教训**：参数调优要基于实际效果，不是越低越好

#### 5. 重复 chunk 影响检索质量

**现象**：相似内容被切成多块，检索结果冗余
**解决**：添加 MD5 去重，相似度 >95% 的 chunk 只保留一个

### 🟢 核心模块设计

#### 6. JWT 鉴权与多租户隔离

**设计目标**：用户数据完全隔离，A 用户无法访问 B 用户的文档和对话
**实现方案**：

- 注册/登录时生成 JWT Token，后续请求携带 `Authorization: Bearer <token>`
- 数据库层面：所有表添加 `user_id` 外键，查询自动过滤
- 文件存储：按 `user_id` 分目录，物理隔离
- 缓存隔离：Redis Key 前缀包含 `user_id`，避免缓存穿透
  **安全加固**：
- JWT Secret 从环境变量读取，禁止硬编码
- Token 过期时间 24 小时，支持刷新机制
- 密码 bcrypt 加密存储

#### 7. 混合检索（Hybrid Search）

**设计目标**：兼顾语义理解和关键词精确匹配
**实现方案**：

```
用户提问
    ├──→ 向量化 (bge-m3) → 向量检索 Top20 (相似度排序)
    └──→ 分词 → BM25 全文检索 Top10 (相关性排序)
                          ↓
                    RRF 融合排名 (k=60)
                          ↓
                    去重（相同 chunk 合并）
                          ↓
                    Rerank 精排 Top5
```

**关键参数**：

- 向量检索：`top_k=20`，L2 距离度量
- 全文检索：`top_k=10`，PostgreSQL tsvector
- RRF 融合：`k=60`（平滑排名差异）
- 最终阈值：`score > 0.001`（兜底保留 5 个）

#### 8. 重排序（Rerank）

**设计目标**：在召回的候选集中，精准找出最相关的片段
**实现方案**：

- 使用 `BAAI/bge-reranker-v2-m3` 对候选 chunk 打分
- 输入：用户问题 + 候选文档片段
- 输出：0-1 之间的相关性分数
- 仅排序不替代分数，避免原始相似度信息丢失
  **流程优化**：

```
混合检索召回 20 个候选
        ↓
Rerank 打分排序
        ↓
取 Top 5 送入 LLM
        ↓
生成带引用来源的答案
```

#### 9. 文档隔离与权限控制

**设计目标**：确保用户只能看到自己的文档，管理员可查看全部
**实现方案**：

- **数据库隔离**：`documents` 表 `user_id` 字段 + 查询过滤
- **文件系统隔离**：上传路径 `uploads/{user_id}/{doc_id}/`
- **API 权限校验**：每个接口通过 JWT 解析 user_id，拒绝越权访问
- **对话隔离**：`conversations` 表同样关联 `user_id`
  **代码示例**：

```python
# 所有查询自动过滤当前用户
documents = await db.execute(
    select(Document).where(Document.user_id == current_user.id)
)
```

### 🟢 工程优化

#### 10. JWT Secret 硬编码安全隐患

**解决**：从环境变量读取，启动时校验是否已修改默认值

#### 11. 外部 API 不稳定

**解决**：LLM 和 Embedding 添加 3 次重试 + 指数退避，失败时降级处理

#### 12. 缓存雪崩风险

**解决**：Redis 缓存带 TTL，热点数据异步预热，缓存失效时互斥锁保护
